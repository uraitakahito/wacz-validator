wacz-validator runs a fixed set of rules over an archive and reports one issue per
violation. [The table](#every-rule) is **generated from the rule definitions
themselves**, so it cannot fall behind the code: name, severity, conformance
level, per-profile overrides and spec links all come out of
`packages/core/src/validate/`.

## Reading the table

**Conformance** is what the spec demands — `MUST`, `SHOULD`, `MAY`, `MUST NOT`.
**Severity** is what wacz-validator does about a violation.

Severity takes one of three values. **Only `error` decides the verdict** — an
archive is usable exactly when `summary.failed` (the `error` count) is zero, and
no number of `warning`s or `info`s overturns that.

| Severity | Meaning | `summary.failed` |
| --- | --- | --- |
| `error` | the archive cannot be used — replay breaks, or the check cannot be made | incremented |
| `warning` | worth fixing, but not broken on its own | unaffected |
| `info` | an observation, carrying no judgement | unaffected |

Severity is decided by one thing only: **whether the archive is usable**. So
[`datapackage/resources-complete`](#datapackage-resources-complete) is a `MUST`
reported as a `warning` — an incomplete `resources[]` does not by itself break
replay.

**When you want the conformance view, read the conformance column.** Handling
the two axes separately is covered in
[JSON report](/wacz-validator/json-report/#severity-and-conformance-answer-different-questions).

### Some rules list two severities

**A rule can report at different severities depending on what it finds.** When it
does, the severity column lists every value it can emit.

[`datapackage/digest`](#datapackage-digest) reads `warning / error`: a missing
digest file only falls short of a `SHOULD`, so it is a `warning`; a file that is
present but whose hash does not match **may mean the archive was altered**, so
that is an `error`. Same rule, different finding, different treatment.

Any rule whose severity column lists more than one value is like this.

`MUST`, `MUST NOT`, `SHOULD`, `SHOULD NOT` and `MAY` carry their
[RFC 2119](https://www.ietf.org/rfc/rfc2119.txt) meanings. The conformance
column is **copied from the specification, not wacz-validator's own grading of how
much a rule matters**.

:::note[Where the sources stand]
Only [Data Package](https://uraitakahito.github.io/datapackage/) says so
outright — each of its specification files opens with "the key words … are to
be interpreted as described in RFC 2119". **WACZ 1.1.1 and 1.2.0 and wacz-auth
0.1.0 use `MUST` and `SHOULD` without ever citing RFC 2119** — checked: the
string does not appear in any of them.

**WARC 1.1 is an ISO standard and uses ISO's verbal forms instead** — lowercase
*shall*, *shall not*, *should* and *may*, never `MUST`. wacz-validator records
*shall* as `MUST`, *shall not* as `MUST NOT`, *should* as `SHOULD` and *may* as
`MAY`.

wacz-validator therefore reads every conformance level it records as RFC 2119 intends,
whichever specification it came from. That follows the convention, but where a
source does not say so, it is wacz-validator's reading rather than the source's
statement.
:::

### The severity column carries the per-profile values

The first line of the severity column is the **default (`--profile spec`)**; the
smaller lines under it are the **per-profile overrides**. A rule with nothing
underneath reports the first line everywhere.

**Not every finding from a rule necessarily moves**, so a count is shown when
more than one does. A line like `browserhive: >=1.11.0` is a **producer version
range**: name a version outside it (`--profile browserhive@1.10.0`) and the rule
does not run, which the report records under `skipped`. Conformance never moves
with the profile — it is what the spec says.
See [Profiles](/wacz-validator/profiles/).

## What the rules are grounded in

Rules fall into groups by the layer they inspect:

- **`wacz/*`** — the ZIP layout itself: which files and directories must exist,
  and what must not be in the reserved ones.
- **`datapackage/*`** — `datapackage.json`: the Frictionless structure, the
  declared `profile`, the WACZ version, and whether the hashes match what is
  actually in the archive.
- **`cdxj/*`** — the index: whether wabac.js can load it, whether its offsets
  point at real WARC records, and whether the filenames are archive-relative.
- **`warc/*`** — inside the WARC. Two kinds sit under this prefix:
  - what [WARC 1.1](https://uraitakahito.github.io/warc-specifications/specifications/warc-format/warc-1.1-annotated/)
    asks of every record, whoever wrote it: the record's shape (version line,
    CRLF, `Content-Length`, the closing CRLF CRLF), the fields it must carry,
    the fields its type must not carry, the form of each field's value, the
    `Content-Type` the standard recommends, `revisit` profiles and segmented
    records. These run under every profile; how each finding is graded is on
    [Profiles](/wacz-validator/profiles/#how-the-warc-11-rules-are-graded).
  - how the WARC is stored and recorded: independently-decodable gzip members,
    payload digests, and whether the recording is complete.
- **`pages/*`** — `pages/pages.jsonl` against its schema.
- **`wacz-auth/*`** — the signature in `datapackage-digest.json`.
- **`browserhive/*`** — BrowserHive's own conventions, from the BrowserHive WACZ
  and WARC profiles. They run only under `--profile browserhive`.

## Why some rules exist twice over

Two rules can look at the same file for different reasons, and that is
deliberate. [`wacz/required-files`](#wacz-required-files) asserts that an index simply **exists**;
[`cdxj/index-recognised-by-wabac`](#cdxj-index-recognised-by-wabac) asserts that wabac.js can actually **load** it.
An archive can pass the first and fail the second, and the distinction is what
tells a producer where the problem is.

Likewise `wacz/required-files` owns the "is `datapackage.json` there at all"
question, so [`datapackage/profile-required`](#datapackage-profile-required) can concentrate on the *value* of
`profile` without reporting the same absence twice.

The WARC 1.1 rules go the other way: **one defect is reported by one rule.** A
record whose shape is broken — a header line that is not a field, a
`Content-Length` that does not match the block — is reported by
[`warc/record-structure`](#warc-record-structure), and the rules that read fields
skip that record, because its fields cannot be trusted. Without that, one
missing colon would surface again as a missing field and a malformed value.

## Adding a rule

A rule is a file under `packages/core/src/validate/rules/` **and** an entry in
that directory's `index.ts`. Both steps are required: an unregistered rule never
runs. The docs build counts the two and fails if they disagree, so a forgotten
registration cannot ship quietly.
