wacz-validator は固定された rule の集合を archive に対して実行し、違反 1 件につき
issue を 1 件報告します。[全 rule の表](#全-rule)は **rule 定義そのものから生成**して
いるので、コードから遅れることがありません。rule 名・severity・適合レベル・profile
ごとの上書き・spec リンクはすべて `packages/core/src/validate/` 由来です。

## 表の読み方

**適合レベル**は spec が要求する強さ(`MUST` / `SHOULD` / `MAY` / `MUST NOT`)、
**severity** は違反に対して wacz-validator が取る扱いです。

severity は `error` / `warning` / `info` の 3 値です。**判定に効くのは `error` だけ**で、
アーカイブが使えるかどうかは `summary.failed`(= `error` の件数)が 0 かで決まります
—— `warning` と `info` は何件あっても覆しません。

| severity | 意味 | `summary.failed` |
| --- | --- | --- |
| `error` | これがあると使えない(再生が壊れる / 検証が成立しない) | 増やす |
| `warning` | 直すべきだが、それだけでは壊れない | 変えない |
| `info` | 観察の記録。良し悪しの判断を含まない | 変えない |

`MUST` / `MUST NOT` / `SHOULD` / `SHOULD NOT` / `MAY` は
[RFC 2119](https://www.ietf.org/rfc/rfc2119.txt) の意味で用います。
表に出る適合レベルは **wacz-validator が付けた重要度ではなく、spec 側の記述を写したもの**です。

severity を決めるのは「**そのアーカイブが使えるか**」だけです。たとえば
[`datapackage/resources-complete`](#datapackage-resources-complete) は `MUST` ですが
`warning` です — `resources[]` が不完全でも、それだけで replay が壊れるわけでは
ないからです。

**仕様準拠の観点で絞りたいときは適合レベルを見ます。** 2 つの軸を別々に扱う方法は
[JSON レポート](/wacz-validator/ja/json-report/#severity-と-conformance-は別の問いに答えます)にあります。

### severity 欄が 2 つ並ぶことがあります

**1 つの rule が、見つけたものによって別の severity を出す**ことがあります。その場合
severity 欄には出しうる値がすべて並びます。

[`datapackage/digest`](#datapackage-digest) は `warning / error` です — digest ファイルが
無いのは仕様上 `SHOULD` 未達なので `warning`、ファイルはあるのに hash が合わないのは
**アーカイブが変更された可能性**を意味するので `error`。同じ rule でも、見つけたものが
違えば扱いも違います。

severity 欄に値が 2 つ以上並んでいる rule が、これに当たります。

:::note[出典側の事情]
明示的に RFC 2119 を宣言しているのは
[Data Package](https://uraitakahito.github.io/datapackage/ja/) だけです
（各仕様書の冒頭に「本文書のキーワードは RFC 2119 に記述されたとおりに解釈される」とある）。
**WACZ 1.1.1 / 1.2.0・wacz-auth 0.1.0 は `MUST` や `SHOULD` を使いながら、
RFC 2119 への言及がありません**（本文中に一度も現れないことを確認済み）。

**WARC 1.1 は ISO の規格で、ISO の言い方を使います** —— 小文字の *shall*・*shall not*・*should*・*may* で、`MUST` は一度も現れません。
wacz-validator は *shall* を `MUST`、*shall not* を `MUST NOT`、*should* を `SHOULD`、*may* を `MAY` として記録します。

そこで wacz-validator は、**どの仕様に由来する適合レベルでも RFC 2119 の意味で扱います**。
慣例に従った解釈であり、出典側が明示していない部分については wacz-validator の側の取り決めです。
:::

### severity 欄には profile 別の値がぶら下がります

severity 欄の 1 行目が**既定 (`--profile spec`) の値**で、その下に字下げして並ぶのが
**profile 別の上書き**です。下に何も無い rule は、どの profile でも 1 行目のまま報告されます。

**その rule の指摘が全部変わるとは限らない**ので、複数が対象なら件数を添えています。
`browserhive: >=1.11.0` のように**バージョンの範囲**が出る rule は、その範囲外を
[`--profile browserhive@1.10.0`](/wacz-validator/ja/profiles/) のように名乗った実行では走らず、
落としたことが JSON の `skipped` に残ります。適合レベルは profile では動きません ——
spec がそう書いている、という事実だからです。
[プロファイル](/wacz-validator/ja/profiles/)を参照。

## rule が見ている層

- **`wacz/*`** — `ZIP file` の構造そのもの。存在しなければならないファイル /
  ディレクトリと、予約ディレクトリに異物が無いか。
- **`datapackage/*`** — `datapackage.json`。Frictionless の構造、宣言された
  `profile`、WACZ version、そして hash が実体と一致するか。
- **`cdxj/*`** — index。wabac.js がロードできるか、offset が実在の WARC record
  を指すか、filename が `archive/` 相対か。
- **`warc/*`** — WARC の内部。この接頭辞の下には 2 種類があります。
  - [WARC 1.1](https://uraitakahito.github.io/warc-specifications/specifications/warc-format/warc-1.1-annotated/) が、誰の書いた記録にも求めること。
    記録の形（版の行・CRLF・`Content-Length`・記録を閉じる CRLF CRLF）、記録が持たなければならない欄、type に書いてはいけない欄、欄の値の形、規格の勧める `Content-Type`、`revisit` の profile、分割した記録。
    どの profile でも走り、指摘の等級の決め方は[プロファイル](/wacz-validator/ja/profiles/#warc-11-の-rule-の等級)にあります。
  - WARC の置き方と記録のされ方。gzip member が独立して展開できるか、payload digest、recording が完結しているか。
- **`pages/*`** — `pages/pages.jsonl` の schema 適合。
- **`wacz-auth/*`** — `datapackage-digest.json` の署名。
- **`browserhive/*`** — BrowserHive の WACZ と WARC の profile が定める、BrowserHive 自身の決まり。
  `--profile browserhive` のときだけ走ります。

## 同じファイルを 2 つの rule が見る理由

観点が違うので意図的にそうしています。[`wacz/required-files`](#wacz-required-files) は index が
**存在するか**を assert し、[`cdxj/index-recognised-by-wabac`](#cdxj-index-recognised-by-wabac) は wabac.js が実際に
**ロードできるか**を assert します。前者を通って後者で落ちる archive はあり得て、
その区別こそが producer に問題の所在を教えます。

同様に `datapackage.json` の存在チェックは `wacz/required-files` が担うので、
[`datapackage/profile-required`](#datapackage-profile-required) は `profile` の**値**に専念できます(不在を
二重に報告しません)。

WARC 1.1 の rule は逆向きで、**1 つの欠陥は 1 本の rule が言います**。
形の崩れた記録（欄になっていない見出しの行、block と合わない `Content-Length` など）は [`warc/record-structure`](#warc-record-structure) が言い、欄を読む rule はその記録を見ません。
欄を信じられないからです。
そうしないと、コロン 1 つの抜けが、欄の欠けとしても値の崩れとしても出てきます。

## rule を追加するとき

rule は `packages/core/src/validate/rules/` にファイルを置き、**かつ**同ディレクトリの
`index.ts` に登録して初めて有効になります。両方が必要で、登録し忘れた rule は
一度も実行されません。docs のビルドが両者の件数を突き合わせるので、
登録忘れが静かに紛れ込むことはありません。
